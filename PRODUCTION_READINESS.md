## Release decision

**Not ready for a private production APK.** The first release is a privately distributed signed APK. The MVP includes SMS forwarding, incoming-call information, notifications, history, recovery, and remote SMS sending on Android 8+ without root. One SIM 1 remote send has been confirmed. On 2026-10-07 the owner deferred SIM 2 carrier validation until after the private MVP while keeping both SIM choices available; private release notes must identify SIM 2 as unvalidated. The owner deferred the separate rooted Samsung SM-A520F live-call beta on 2026-10-06; keep it disabled and do not gate the private MVP on its call test.

Decisions recorded 2026-10-01 through 2026-10-03: private signed APK first; include remote SMS; offer only FCM on demand and WebSocket; transfer the first secure pairing invite by copying and entering its text. The owner keeps a newly created signing key locally. When the creator deletes a secure pairing, revoke both devices and erase queued relay data. The custom Firebase Realtime Database transport is retired. Saved pairings using it stay visible with migration guidance and cannot connect; the project owner must remove any data and unsafe rules left in old Firebase projects.

The recommended order is: secure pairing and data lifecycle; reliable baseline delivery; release automation and supported devices; then public distribution. Do not deploy the stronger pairing mode before both Android clients and the Worker can use it.

## MVP roadmap

### M0 — freeze the promise and distribution path

- Freeze the chosen first distribution as a private signed APK with remote SMS and only FCM/WebSocket. Keep rooted live calls behind a separate feature flag until its gates pass.
- Inventory the exact Worker version, Firebase project, TURN credentials, installed APK versions, and branch used by the two test phones. Record without exposing tokens or message content.
- Define supported Android versions and device matrix: sender API 26, receiver API 34/35/36, Samsung SM-A520F, Xiaomi 23049PCD8G, and at least one clean non-root sender.

**Exit:** one release scope, one branch, one backend environment, one device matrix, and a known rollback build.

### M1 — close the security and privacy blockers

- Finish the locally integrated secure pairing protocol in Worker and Android. The copyable invite expires after 15 minutes and is single use; local tests cover create/join, WebSocket access, owner deletion, and provisional rate limits. The owner approved revoking old pairings and re-pairing with fresh copied invites for the private MVP. Deploy/review the limits and expiry/purge, test every endpoint, and retire legacy code-only routes after old clients move. Test the backend migration without token takeover; preserve old local history only if the verified backup can be restored.
- Migrate existing custom Firebase Database pairings to new relay pairings on both phones; retain their local history, verify delivery, then remove old cloud data and lock down old project rules. The release APK must contain no Database SDK or setup option.
- Protect local credentials and content, define server/local retention, deletion and export behavior, lock-screen redaction, and release-log filtering. Document that the relay can see SMS/call metadata unless application-level encryption is added.
- Restrict production to TLS endpoints and prevent debug/LAN settings from entering a signed public build.

**Exit:** adversarial API tests and two-phone upgrade tests show no code-only access, cross-pair access, stale-token access, or retained data after deletion.

### M2 — prove baseline behavior

- Fresh pair and self-test without ADB in under five minutes. All permission denials and offline states show an action to recover.
- Exercise 20 mixed SMS events, incoming call `RINGING`/`OFFHOOK`/`IDLE`, stacked notifications, message history, event deduplication, and restart/reboot persistence.
- Exercise screen-off/Doze, Wi-Fi to cellular handoff, 24-hour offline interval, Worker restart, FCM token rotation, full queue, queue overflow, and sender/receiver app upgrades. Require fetch/ack evidence before treating an event as delivered.
- Test new ringtone behavior and notification privacy on both reference phones. Capture logs and screenshots with personal content redacted.

**Exit:** the release candidate passes the baseline matrix on physical phones; no silent loss or duplicate visible event in tested recovery paths; unsupported live-call actions stay hidden.

### M3 — remote SMS release gate and rooted call beta

- Remote SMS: validate both SIMs, selected-SIM mismatch failure, multipart and Unicode, callback error reporting, idempotency, and no automatic repeat after an uncertain modem result. This is required before the private MVP APK ships; use an owner-approved recipient and text for live sends.
- Rooted call beta: test 10 controlled setups, five-minute speech both ways, network interruptions, hang-up, mixer restoration, TURN expiry/rotation, and quality metrics without recording raw audio. Label supported model/firmware precisely.

**Exit:** each feature ships only with its own evidence; failure leaves the baseline relay usable.

## Production roadmap

### P0 — release pipeline and platform migration

- Upgrade toolchain and target to API 36 for the later Play/public release, review foreground-service, notification, full-screen intent, and background execution behavior on Android 15/16, and rerun the API 26 gateway regression matrix. For the private APK, first prove the supported-device matrix on the current target and record the API migration as production follow-up.
- Supply Firebase config to CI securely. CI must run Python smoke/TLS/security tests, Worker unit/integration tests, Android unit tests, lint, signed release build, dependency/security scan, and artifact checks. Record commit, backend version, SHA-256, versionCode, signing identity, and migration order.
- Add staged deployment with backend-before-client compatibility checks, canary install, rollback rehearsal, and release notes. Separate production and test Firebase/Worker resources.

**Exit:** a clean checkout can produce a reproducible, signed release candidate; the previous client continues working during backend rollout and the rollback procedure is rehearsed.

### P1 — policy, operations, and support

- For Google Play, prepare the SMS/Call Log permissions declaration and document the cross-device synchronization use case, prominent disclosure and consent, privacy policy, Data safety form, and full-screen-intent use. Google reviews exceptions case by case. If approval is unavailable, use a distribution route whose requirements and user risks are explicitly accepted.
- Add content-free health checks, redacted error/latency metrics, queue age/overflow counters, FCM/TURN failure rates, alerting, incident runbook, backup/restore rehearsal, credential rotation, support diagnostics, and a user-facing delete-pairing path.
- Run a small opt-in beta with crash, delivery, battery, and support thresholds before a wider release.

**Exit:** policy approval or a documented alternative distribution decision; operational owner can detect and recover from failed delivery without accessing personal content.
